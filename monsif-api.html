Conventions

Uniform across every endpoint, so you can write one fetch wrapper and one error path.

Response envelope
// success — always 200
{ "status": "success", "data": { ... } }

// failure — 400, 404, 500, 502 or 503
{ "status": "error", "error": "رسالة بالعربية" }

Errors come back in Arabic. The error string is user-facing prose, safe to display directly. Branch on the HTTP status code, not on the message text.

Search response shape

All four search endpoints (laws, cases, contracts, and search) return the same outer fields inside data:

FieldTypeMeaning
querystringEcho of what you sent — useful for discarding stale responses.
foundbooleanWhether anything passed the threshold.
countintegerLength of results.
resultsarrayThe hits. Shape differs per endpoint.
messagestring | nullArabic "nothing found" text when found is false. Render it as the empty state.
params_usedobjectEvery parameter actually applied, defaults included. Ideal for a debug panel.
took_msintegerServer-side duration.

found: false is a success, not an error. It arrives as HTTP 200 with an empty results array. Show message rather than an error toast.

Parameter precedence

Defaults in config.py are overridden by .env, which is overridden by fields in the request body — and a body field affects only that one request. Send just text and you get server defaults. Every /config endpoint reports the live defaults plus the exact list of names that request bodies may override, so the frontend can build a tuning panel without hardcoding anything.

How features relate

Six features are independent. Judgment prediction is not — it calls two of the others internally before it reaches the LLM, which is why it is by far the slowest endpoint.

Because judgment prediction re-runs retrieval itself, you do not need to call /laws/search and /cases/search first and pass the results in. Send the raw facts. The statutes and precedents it used come back in the response under _retrieved_statutes and _retrieved_cases, so you can render the evidence alongside the verdict.

Laws catalog

Browsing rather than searching: list the laws, then open one and read its articles grouped into that law's own internal structure. Reads the corpus file directly — no models, no Qdrant lock, so every call is instant even on a cold server.

The corpus holds 25 laws and 2,278 articles. Each law carries an internal hierarchy of كتاب › باب › فصل — that is what "category" means here. It is structure within a law, not a classification of laws. Twelve of the amnesty decrees additionally carry a top-level category of تشريعات العفو العام; the other thirteen have null.

GET/api/legal/lawsinstant

Every law with its article count, internal category count, and status breakdown. Sorted by article count, largest first.

Query parameters
ParamDefaultWhat it does
q—Substring match against law name, short name, or id. This is what you want to search laws by name.
category—Exact top-level category. The only value present in the corpus is تشريعات العفو العام.

category is not a law name. Only 12 amnesty decrees carry a category; the other 13 laws have null. Passing a law's name as category correctly matches nothing — to find a law by name use ?q=, and to open one use the articles endpoint. Every response lists the valid values in available_categories, and a filter that matches nothing returns an Arabic message explaining why rather than a bare empty list.

Stray quotes are tolerated. Typing ?category="…" straight into a browser makes the quote marks part of the value, which silently matches nothing. The API now strips surrounding ", ', «» and curly quotes from q, category, status, law_id, and article_id. Note that percent-encoding like %D9%82%D8%A7 in the address bar is normal and correct — Arabic URLs always look like that, and the server decodes them fine.

Laws RAG

Hybrid dense + sparse retrieval over 2,278 articles in Qdrant, fused with RRF, reranked by a cross-encoder, then merged with each hit's linked articles.

POST/api/legal/laws/searchCPU-bound · ~7–13s warm
Request
FieldDefaultWhat it does
text—Required  The facts or legal question.
top_n7Articles in the final result.
hybrid_top_k15The only real speed dial. Candidates entering the reranker — cost is roughly linear in this number. 15→10 saves about a third.
exclude_repealedfalseDrop articles marked ملغاة.
min_score0.05Absolute floor; hits below are discarded. Your .env pins this to 0.0, which overrides the default — the two relative cutoffs below do the filtering instead.
min_score_ratio0.15Relative floor: drop anything below ratio × top score. Adapts to the query — a strong match raises the bar, a weak one lowers it. 0 disables.
score_drop_ratio0.5Cut the tail at the first sharp fall: when an article scores below ratio × the one above it, it and everything after are dropped. 0 disables.
with_dependenciestrueAttach the articles each hit references.
dep_depth21 = direct references only; 2 = also their references.
dep_max12Cap on merged articles per hit.
dep_dedupe_vs_hitstrueDon't repeat an article that is already a top-level hit.
decomposefalseSplit long facts into separate legal issues. Needs GOOGLE_API_KEY; adds an LLM call.
rerank_max_length512Cross-encoder window. Barely affects speed here — article bodies are short (typically 50–600 characters), so they rarely reach even 256 tokens. Measured: 256, 512 and 1024 all take the same time.
Why it is slower than Colab

Measured on this machine, warm, for one query with hybrid_top_k=15:

StageTimeShare
BGE-M3 encode (dense + sparse)0.23 s~3%
Qdrant hybrid search + RRF0.30 s~4%
Cross-encoder rerank7–13 s~93%

The reranker is the whole cost, and the difference is GPU versus CPU. bge-reranker-v2-m3 is a 568M-parameter cross-encoder that runs one full forward pass per candidate. Colab gave it a GPU; this machine has none (cuda: False, so fp16 is off too). The same 15 forward passes that take a fraction of a second on a T4 take several seconds on CPU. Nothing in the retrieval code changed between the notebook and here — the hardware did.

If you get a GPU, set DEVICE=cuda in .env and this drops back to notebook speed immediately.

Two things were tried and rejected: int8 dynamic quantization gave only 1.29× and wrecked the ranking (rank agreement 0.2 against the fp32 scores), and shortening the rerank window does nothing because the bodies are already short. What did work is length-bucketed batching — see below.

The 2.15× speedup that was applied

The reranker padded every pair in a batch to the length of the longest one, so a single long article forced all 15 through a full-width forward pass. Sorting candidates by body length and using small batches (4 on CPU) groups similar lengths together and cuts the padding waste.

Batching4 queriesSpeedup
Before — one batch of 16, unsorted70.75 s1.00×
After — batches of 4, length-sorted32.84 s2.15×

Scores are bit-identical — this changes only how work is grouped, never what is computed, and results come back in the original order. Cases RAG shares the same reranker and gets the same speedup for free.

Three filters run after reranking, in order. The top hit always survives if it clears the absolute floor.

Judgment prediction

The flagship feature and the slowest: it runs both retrieval pipelines, optionally consults the statistical classifier, makes up to five LLM calls, then verifies that every citation genuinely appears in the retrieved context.

Blocked until GROQ_API_KEY is set. Without it this endpoint returns 503 with an Arabic message. Check groq_api_key_set on /judgment/config at app startup and hide or disable the feature rather than letting users hit a wall.

fully_grounded is the single flag to gate your UI on. It is true only when every citation resolves, every supporting quote really appears in its article, and no precedent contradicts the chosen article. When it is false, the non-empty arrays tell you exactly which claims to mark unverified — show the verdict with a warning rather than suppressing it.

Failure modes

If the LLM returns unparseable output you get HTTP 502 with status: "error" and a data object still containing retrieved_statutes and retrieved_cases. You can still show the retrieved context and offer a retry.

GET/api/legal/judgment/configinstant

Beyond defaults, this reports groq_api_key_set, classifier_available, and a depends_on object showing whether Laws RAG and Cases RAG are already loaded — everything you need for a feature-availability check at startup.

Contract templates

Semantic search across 211 contract templates, then retrieval of the full document. Deliberately two steps: the suggestion layer recommends, the user decides.

POST/api/legal/contracts/getstep 2

Send {"doc_id": "..."} — or {"subject": "..."}, which must match a search result exactly. Sending neither is 400; matching nothing is 404.

placeholders is your form. The template body carries inline tags of the form [[n:label]]. Parse them into labelled inputs, let the user fill them, and substitute back — that turns this endpoint into a contract generator rather than a viewer. raw_body is the untagged original if you would rather show clean text.

GET/api/legal/contracts/<doc_id>alias

GET-style equivalent of the previous endpoint. URL-encode the id. Note that /contracts/config resolves to the config route, so a template whose id is literally config is unreachable here — use the POST form.

GET/api/legal/contracts/configinstant

Defaults, tunable names, embedding_model, and loaded. Once the index is loaded it also returns total_contracts and categories — a category-to-count map that makes an excellent browse-by-category landing view without any extra endpoint.

Errors

Same envelope everywhere. The status code tells you how to react; the Arabic error string is safe to show as-is.

CodeMeansWhat the frontend should do
400Missing or empty text / facts, text too short, bad mode, uncastable parameter.Validate before sending; show the message inline on the field.
404No contract matches the doc_id or subject.Send the user back to search results.
500Unexpected server error.Generic retry.
502Judgment only — the LLM returned unparseable output.Offer retry; data still holds the retrieved context, so show that.
503Feature unavailable: index not built, or GROQ_API_KEY missing.Not transient — retrying won't help. Disable the feature and surface the message to whoever runs the server.

Frontend notes

Things that will bite you if you discover them during integration instead of now.

ConcernWhat to do
TimeoutsDefault fetch behaviour is fine for instant endpoints, but a warm RAG call still takes ~7–13 s on this CPU-only machine (first call adds ~7 s of model loading), and judgment can run for minutes. Set generous per-endpoint timeouts and never a single global 30 s.
Cold startPoll /api/health on load. If the feature is not loaded, say the model is being prepared and give a realistic estimate instead of an ambiguous spinner. Expect roughly 7 s of loading, then 7–13 s per query.
ConcurrencyThe server is threaded but CPU-bound, and Qdrant takes an exclusive lock. Two heavy searches at once will both crawl — queue requests client-side rather than firing in parallel.
RTLContent is Arabic; set dir="rtl" on containers rendering it. Keep article_id, doc_id, and JSON debug output LTR, or mixed Arabic-and-punctuation ids will display scrambled.
Score scalesLaws RAG gives similarity_score as 0–100; Cases and Contracts give 0–1. Don't share one formatter.
Input field nameEvery endpoint takes text except /classify, which takes facts.
Ids in URLsarticle_id and doc_id contain Arabic and colons. Always encodeURIComponent them, or prefer the POST variants.
Empty resultsfound: false arrives as HTTP 200. Render message as an empty state, not an error.
Browse vs searchUse the catalog endpoints for navigation — they are instant and need no models. Reserve /laws/search for actual semantic queries, since it costs several seconds even warm. Both return the same article_id, so results link together.
Debug panelEvery search echoes params_used and took_ms. A collapsible panel showing them makes tuning thresholds vastly easier during development.
Feature flagsCall the four /config endpoints once at startup. They tell you what is loaded, whether the Groq key is set, and which parameters the UI may expose — no need to hardcode any of it.
